## 0. 🔒 규제 게이트 (최우선 — 셋이 다 열리기 전엔 구현 착수 금지)

상품 후원은 **응원 한잔·나와의 내기가 넘은 게이트보다 하나 더 높은 문**을 통과해야 한다.

| # | 게이트 | 근거 | 상태 |
|---|--------|------|------|
| **①** | **경품류 제공 규제 자문** — 표시광고법상 경품류 제공 고시(소비자 현상경품 한도) + 협찬 표시 의무 | [`PHASE2_FINTECH_PLAN.md:310`](PHASE2_FINTECH_PLAN.md) *"협찬 경품은 경품류 제공 규제 별도 자문 필요"* | ⛔ **미착수** |
| **②** | **⑤b 실돈 전환** — PG(토스페이먼츠)·기프티콘 B2B·휴대폰 본인인증 **실계약**. 현재 셋 다 mock([`providers.ts`](../supabase/functions/_shared/payments/providers.ts) — 네트워크 호출 0건) | [`PHASE2_FINTECH_PLAN.md:289`](PHASE2_FINTECH_PLAN.md) ⑤b 미체크 | ⛔ **미착수** |
| **③** | **순서** — 응원 한잔·나와의 내기 베타 오픈(⑤b) **후** 본격 설계 | [`PHASE2_FINTECH_PLAN.md:309`](PHASE2_FINTECH_PLAN.md) §8 | ⛔ **⑤b 선행** |

**게이트 ① 은 ⑤b 4개 안건(ⓐ~ⓓ) 밖의 추가 게이트다.** ⑤b 자문은 도박·기부금품·청약철회·미성년(내기 축)을 다루지만, 상품 후원의 **경품류/협찬 표시**는 그 목록에 없다 → [`PHASE2_FINTECH_PLAN.md:162`](PHASE2_FINTECH_PLAN.md) 안건 목록에 미포함. 즉 이 트랙은 **⑤b 통과 + 경품 자문 통과** 를 둘 다 요구한다.

> 결론: **이 문서가 만들어질 수 있는 시점 = 세 게이트가 다 열린 뒤.** 그 전까지 아래 §3~§6 은 전부 *제안/자문대기* 이며, 확정된 것은 §0(게이트 존재)과 §1(형태 1과의 경계)뿐이다.

## 1. 한 줄 정의 + 형태 1(매칭 기부)과의 경계

**상품 후원(형태 2) = 조직/명사가 하다에 실물 상품(기프티콘·굿즈·인증서)을 걸고, 완주자에게 앱을 통해 지급하는 후원.**

핵심은 **"앱을 통한 실물 지급"** — 여기서 규제 강도가 형태 1과 갈린다.

### 형태 1(매칭 기부, 이미 구현) vs 형태 2(상품 후원, 이 문서)

| 축 | 형태 1 — 완주 매칭 기부 (구현 완료, [`0075`](../supabase/migrations/0075_sponsor_matching.sql)) | 형태 2 — 상품 후원 (이 문서, 미구현) |
|---|---|---|
| **돈·물건이 앱을 흐르나** | ❌ **0원·0건.** 앱은 약정 문구와 완주 수만 **표시**. 송금은 조직이 오프라인 직접 | ✅ **흐른다.** 앱이 기프티콘을 발급·전달(완주자 휴대폰/바코드) |
| **참여자↔재화 이전** | 조직 → 제3자(기부처)만. 참여자는 아무것도 받지 않음 | 조직 후원 → **참여자(완주자)가 실물 상품 수령** |
| **gift_orders 사용** | ❌ 미사용 — 결제·발급 파이프라인 안 탐 | ✅ 사용(확장) — 발급·상태머신 필요 |
| **닿는 규제** | 표시광고법(약정 주체 표시)만. 결제·도박·전자금융·경품 **전부 무관** | 표시광고법 **+ 경품류 제공 규제 + IAP + (기프티콘)전자상거래·청약철회** |
| **구현 게이트** | 없음 (mock 상태와 무충돌) | §0 게이트 3중 |
| **근거** | [`WORLDWIDE_EXECUTION_PLAN.md:188`](WORLDWIDE_EXECUTION_PLAN.md) 형태 1 · [`ORG_HADA_PLAN.md:146-152`](ORG_HADA_PLAN.md) Step 4-a | [`WORLDWIDE_EXECUTION_PLAN.md:189`](WORLDWIDE_EXECUTION_PLAN.md) 형태 2 · [`ORG_HADA_PLAN.md:153-164`](ORG_HADA_PLAN.md) Step 4-b |

**규제 강도가 다른 이유(확정):** 형태 1은 [`0075`](../supabase/migrations/0075_sponsor_matching.sql) 머리말이 명시하듯 *"앱으로 돈이 1원도 흐르지 않는다"* → 규제와 구조적으로 무관하다. 형태 2는 **앱이 실물(경품)을 참여자에게 지급하는 순간** 경품류 제공 주체가 되어 규제 안으로 들어온다. 같은 "스폰서십"이라도 재화 이전 구조가 달라 별개 트랙이다.

> 참고 — 형태 3(표시): 조직 노출 = HostBadge + 안내문뿐([`WORLDWIDE_EXECUTION_PLAN.md:190`](WORLDWIDE_EXECUTION_PLAN.md)). 이미 [`HostBadge.tsx`](../mobile/components/HostBadge.tsx)·[`0073`](../supabase/migrations/0073_invite_host_badge.sql)로 구현됨. 이 문서 범위 밖.

## 2. 결정해야 할 것 — 자문 안건 (전부 *자문에서 확정*, 답을 지어내지 않음)

> 아래는 **질문**이다. 옆의 "쟁점 메모"는 방향 참고일 뿐, **법적 결론이 아니다.** 확정 표기가 붙기 전엔 모두 열린 상태.

| 안건 | 질문 | 쟁점 메모 (자문 참고용, 결론 아님) | 데이터 모델 영향 |
|------|------|-----------------------------------|-----------------|
| **가-1** | 완주자에게만 주는 조건부 지급이 **'소비자 현상경품'** 인가, 아니면 **순수 협찬(경품 아님)** 인가 | "완주"라는 조건 충족자에게 주는 것이 경품 고시상 '현상경품(우연·능력에 따른 제공)'에 해당하는지 vs 후원사가 대가 없이 주는 협찬물인지에 따라 한도 규제 적용 여부가 갈림 | 지급 트리거를 '완주 판정'에 묶을지, '추첨'을 허용할지 |
| **가-2** | 경품에 **한도**가 걸리나 (걸린다면 얼마) | 현상경품 한도 규정이 적용되면 1인당·총액 상한이 데이터 모델의 `amount`/재고 상한에 직접 반영됨 | 티어 상한·수량 상한 값 |
| **나** | **표시·광고 의무** — 협찬 표시 문구, "OO가 후원" 명시 강도 | 형태 1의 카피 원칙([`0075`](../supabase/migrations/0075_sponsor_matching.sql) 머리말 — 주어=조직, "앱의 보증이 아니다") 승계 필요 여부. 협찬임을 완주자·비완주자가 모두 인지해야 하는지 | 카피 상수, 표시 위치 |
| **다** | **미성년 완주자 수령** — 만 19세 미만이 완주했을 때 상품을 받을 수 있나 | 응원 한잔은 "수령은 증여라 리스크 없음, 수신자 인증 불필요"([`PHASE2_FINTECH_PLAN.md:244`](PHASE2_FINTECH_PLAN.md))로 정리됨. 경품은 규제 축이 달라(경품 고시·청소년) 그대로 승계 가능한지 미확정 | 수령 시 인증 게이트 필요 여부 |
| **라** | **기부처 구조 a/b/c 와의 관계** — 미수령·유효기간 만료분을 어디로 보내나 | [`PHASE2_FINTECH_PLAN.md:207-212`](PHASE2_FINTECH_PLAN.md) 3안(물품 기부/회사 약정/플랫폼 연동) 중 미수령분 처분을 어디에 태울지 | 미수령분 상태 전이(donated/refunded) |
| **마** | 후원 재화가 **앱 마진을 태우나** — 태우면 IAP 30% 트리거 위험 | [`PHASE2_FINTECH_PLAN.md:57`](PHASE2_FINTECH_PLAN.md): 마진 떼는 순간 3.1.3(e) 실물 예외가 깨질 수 있음. 형태 2는 조직이 비용을 대므로 앱 마진 0으로 설계할지 | 정산 구조·수수료 필드 유무 |

**미결로 남기는 것(자문 전까지 값을 못 박지 않음):** 지급이 현상경품인지, 한도 숫자, 협찬 표시 강도, 미성년 수령 가부, 미수령분 처분처. 이 값들이 §3 데이터 모델의 컬럼·CHECK·상한을 결정한다.

### 3.1 재사용 가능한 것 vs 새로 필요한 것

| 항목 | 현재 상태 | 상품 후원에 필요한 것 | 분류 |
|------|-----------|----------------------|------|
| 주문 유형 `order_type` | CHECK `('cheer','bet')` 2종 ([`0032:69`](../supabase/migrations/0032_identity_gift_orders.sql)) | `'sponsor'` 유형 신설 | 🆕 **새로 필요** |

### 3.2 "새로 필요"로 분류된 것 요약 (자문 후 설계 확정 대상)

1. `order_type='sponsor'` 신설 (CHECK 확장)
2. 방 외부 주체(스폰서) 허용 — `orderPolicy` 의 "sender·recipient 둘 다 멤버" 요건 우회 분기
3. 조건부(완주 시) 1:N 배분 로직 — 스폰서 주문 1건이 완주자 N명에게 발급
4. 주문↔수령자 1:N 모델 (현 `recipient_id` 단일 컬럼으로는 표현 불가)
5. 재고·수량 상한·소진 개념 (현재 전무)

> **결정 보류:** 위 5개의 구체 스키마(별도 `sponsor_orders` 테이블 신설 vs `gift_orders` 확장, 배분 테이블 형태)는 §2 자문이 경품 한도·현상경품 여부를 확정한 뒤에 정한다. 지금 스키마를 확정하면 재작성된다.
